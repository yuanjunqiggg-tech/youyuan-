# 多维抓包：常驻维度不限于 3 个（可加 dm 等）

改动文件（只碰了自己拥有的）：
- `upstream/youyuan_global_capture.go`
- `upstream/youyuan_capture_runtime.go`（只改方法文档字符串）
- `upstream/frontend/js/youyuan_global_capture.js`

未改主控刚定的两处：`yyGlobalBodyRadius` 未设置仍返回 **48**；`ResidentObservers` 上限仍为 **16**。

## ① 维度键的新校验规则

`dimension_accounts` / `dimension_game_modes` / `dimension_list` 的键不再限定 `"0"/"1"/"2"`：

- 格式：`^[a-z0-9_:.-]{1,40}$`（小写字母、数字、`_ : . -`，1～40 位）。空串、`DM`、`dm!`、`维度` 一律拒绝，报「维度标识需为1～40位小写字母、数字或 _ : . -，例如 dm、dye_dim」。
- 条目上限：三张表（含 `dimension_list`）去重后 **≤ 8**，超出报「维度条目最多8个，当前N个」。
- 唯一性：同一账号仍只能负责一个维度（老约束保留）；另外新增「同一维度只能有一个条目」——`overworld` 与 `0` 同时出现会报「维度0与overworld指向同一游戏维度，请只保留一个」。
- 兼容：内部仍用 `0/1/2` 表示主世界/下界/末地，老 `global-capture.json` 不改也能跑；键顺序固定（内置 0/1/2 在前，其后按 `dimension_list`），同一份配置多次保存结果稳定。
- 别名解析 `yyCaptureDimensionKnown`：`0|overworld|minecraft:overworld|theworld → 0`，`1|nether|the_nether|minecraft:nether|minecraft:the_nether → 1`，`2|end|the_end|minecraft:end|minecraft:the_end → 2`。`dm`、`dye_dim` 这类**合法但暂时映射不到**的标识原样保存。
- `dimension_landings` 仍只收 `0/1/2`，但错误信息改成「维度dm暂不支持指定上线坐标，落点救援目前只支持0/1/2」。原因见 ③：`yyCaptureLandingsValidate`/`yyCaptureArmLanding` 不在我可改范围，存下非 0/1/2 的落点会让 `yyCaptureArmLanding` 整张表校验失败，**所有账号都起不来**（`youyuan_accounts.go:189` 直接 return error）。宁可拒绝并说清，也不落地后静默失效。
- 新增配置字段 `DimensionList []string`（json `dimension_list`）：记录界面上排出来的维度条目（含还没指定机器人的），前端保存时一并回传，刷新后新加的 `dm` 不会消失。

新校验真的在保存路径上：`POST /api/youyuan/global-capture` → `yyGlobalCaptureValidate(c, actor)`（`youyuan_global_capture.go:383` 调用点未变），上面所有规则都在该函数内执行。

## ② 前端加维度交互

`frontend/js/youyuan_global_capture.js`：

- 三个内置维度之后是「＋ 添加维度」按钮（`#yy-gc-dim-add`）；点开出现输入框（`#yy-gc-dim-new`，placeholder `dm`）+ 添加/取消，回车等同添加。校验与服务端同一条正则、同一别名表（`yyCaptureDimResolve`），重名、同维度别名、超 8 条都会就地提示，不提交脏数据。
- 自定义行有「删除该维度」按钮（内置 0/1/2 不允许删）。增删后按草稿重绘，已选的机器人/模式/落点不丢。
- 维度行改成动态渲染（原来只有 3 个固定 `<select>`），每行 = 负责机器人 + 进入时的模式 + （内置维度）指定上线坐标；自定义维度那行写「其他维度暂不支持指定上线坐标」，不给会报错的控件。
- 常驻数量联动：`#yy-gc-residents`（1..16）改动即刷新 `#yy-gc-dim-summary`。维度条目少于数量时提示「当前只有 N 个维度，多余的常驻不会生效」；未指定任何维度机器人时按后端轮转逻辑算 3 个；维度分工关闭时改提示「维度分工已关闭，只按账号顺序轮转」；含 `dm` 时追加「dm 暂无法调度，配置已保留」。
- 每维度机器人数量：行尾提示由后端 `dimension_entries` 驱动——「该维度 N 台机器人正在抓包」/「已分配 N 台…等待连接进入」/「暂无机器人抓包」；`dm` 这类显示「服务端维度模型暂未提供该标识：配置保留，运行时跳过并记一条 warn」。点「刷新运行状态」会用最新数据重算。
- 简单模式页（非管理员）也调用同一个 `yyCaptureDimMount`，不再出现空下拉；保存 patch 里带上 `dimension_landings/game_modes/list`，不动账号分工。

## ③ 运行时遇到未知维度

`yyGlobalDimensionAssignments`（`youyuan_capture_reconcile.go`、`youyuan_capture_plan.go`、`youyuan_capture_landing.go` 都走它）：

- 逐键 `yyCaptureDimensionKnown`；映射不到就 `continue`，**不赋值、不 panic、不按 0 兜底**（按 0 会把机器人 TP 到主世界，是更坏的结果）。
- 每个未知键只记一次 `log.Printf("[global-capture] warn: 维度 %q 暂无法映射到主世界/下界/末地，本轮跳过该维度（配置保留）")`。reconcile 每轮都会进来，不做去重会刷满日志。
- 同一账号出现在多个维度时按固定键序只取第一个，避免 map 随机序导致身份抖动。
- 新增 `yyGlobalDimensionEntries`：接口回 `dimension_entries`（`key/schedulable/accounts/workers`）与 `dimension_limit=8`，前端据它显示「几台在抓」和「能不能调度」。
- `dimension_landings`/`dimension_game_modes` 的运行时读取方式没变（仍按 `fmt.Sprint(维度编号)`），不会因为多了一个 `dm` 键而取错值。

## ⑤ 还需要主控做什么

1. **dm 真正进入维度还缺一层**：现在 `dm` 只是「能配、能存、不崩、会 warn」。要真把机器人放进 dm，需要
   - `youyuan_observer_watch.go:515 yyWatchDimension(int32)` 目前只认 0/1/2，`default` 回落 `overworld`；
   - `yyCapturePlayers`（`youyuan_capture_runtime.go:503`）用 `r.Dimension <= 2` 过滤；
   - `observerBridge.assignDimension` 和 `querytarget` 都只吃数字维度。
   即需要「服务器自定义维度标识 ↔ 数字编号 / `execute in <id>` 字符串」的映射表，这属于维度引擎，不在我 5 个文件内。
2. **落点坐标要不要支持 dm**：`yyCaptureLandingsValidate`（`youyuan_capture_landing.go:19`）硬编码 0/1/2，且 `yyCaptureArmLanding:85` 用**整张表**校验——一旦存了 `dm` 落点，所有采集账号上线都会失败。要支持必须改那个文件（不是我的），我这边只做了拒绝 + 明确文案。
3. **非管理员常驻数仍被写死 3**：`yyGlobalCaptureForActor` 里 `c.ResidentObservers = 3`（`youyuan_global_capture.go`，非我引入）。所以普通用户界面上填 1..16 实际不生效；是否放开、放开到几，属于配额策略，请主控定。
4. 提示语「多余的常驻不会生效」是文案层面的提醒：`yyCaptureConfiguredDesired` 会把 `ResidentObservers` 当总观察机数下限，多出来的机器人在没有对应维度时会作为机动观察机/待探测使用，并不会真的「闲置」。若要求严格按维度数截断，需要改 `youyuan_capture_plan.go`（非我的文件）。
5. 前端 `dimension_list` 是新字段，若别的端（App 旧版本/其他页面）会整体回写 config，注意别把它清空；旧客户端不带该字段时后端按 accounts/modes 的键还原，不影响。

### 1.3 ELF 实际属性（对产物解析程序头得出）

`e_type=ET_EXEC`（**非 PIE**，主程序不吃 ASLR）；`PT_GNU_STACK=RW`（NX 生效，栈不可执行 ✅）；
`PT_GNU_RELRO`/`PT_GNU_PROPERTY` 均无；`.dynsym` 不存在（无动态节，故无 GOT/PLT）。

这解释了清单里一批「编译器加固项」为什么做不了：`-fstack-protector-strong`、`-D_FORTIFY_SOURCE=2`、
`-Wl,-z,relro,-z,now`、`-fcf-protection`、「.dynsym 伪造」、「GOT-PLT 混淆」——
全部作用于 **C 代码或动态链接结构**，而本产物是 `CGO_ENABLED=0` 的纯 Go 静态二进制，
没有 C 栈帧、没有 PLT/GOT、没有动态符号表，加了是空操作。这不是偷懒，是目标文件格式决定的。

### 1.4 APK 构成（改前 83,860,135 B）

`lib/*/libyouyuan.so` 52.8+50.2 MB、`lib/*/libyy_tunnel.so` 29.6+27.7 MB、`libpython3.12.so` 6.3×2 MB。
体积 95% 是 native 库，DEX 只占极小一块——「混淆 DEX」对逆向成本的影响远小于「把 x86_64 那套 82MB 砍掉」，

## 二、本次实际改了什么

### 2.1 构建参数（`build.ps1`）

```
-s -w                         → -s -w -buildid= -X main.buildStamp=<yyyyMMdd-HHmmss-随机6位>   （Win/Linux）
-s -w -checklinkname=0        → -s -w -checklinkname=0 -buildid= -X main.buildStamp=<同上>      （Android .so）
```

`-buildid=` 清掉 Go 自带 build id，两份产物无法从内部指纹互相定位；`-X main.buildStamp=` 把「哪一次构建」
写进二进制，线上崩溃/安全日志能对回构建批次。
新增 `-Pie` 开关（默认关）：开启后 Linux 产物变 `ET_DYN`，主程序也吃 ASLR。
  默认不开的原因写在脚本注释里——现在是全静态 `ET_EXEC`，任何发行版丢上去都能跑；
  PIE 会引入对 `/lib64/ld-linux-x86-64.so.2` 的硬依赖，musl/极小镜像上直接起不来。
  已验证 `-buildmode=pie` 能编过（60,612,872 B，`e_type=3`），开不开由运维确认目标机后定。
- 构建后自动调用封印脚本，失败即 `throw`：宁可构建失败，也不产出未封印的包。

### 2.2 启动自检（新增 `upstream/protect_selfcheck.go`，314 行）

**（a）自身完整性自校验——封印槽方案。**
不能用 `-X main.selfHash=<hash>`：注入的字符串本身会改变二进制，注入的 hash 永远不可能等于产物 hash，死循环。
改成**预置槽位 + 构建后回填**：源码写死 `"YYSEALSC1" + 64 个 '0' + "YYSEALEND"`（`protect_selfcheck.go:52`），
Go 把常量拼接折叠成一段连续字节稳定落在 `.rodata`；构建后由 `maintenance/seal_binary.py`
把槽位清零、对整文件求 sha256、再写回槽位；运行时 `yySealVerify`（`:90`）按结构定位槽位、当 64 个 `'0'` 重算比对。
防绕过：记录必须恰好出现 1 次（`yySealSlots`，`:127`），多于 1 次判为「塞了第二份自洽假记录」直接 mismatch。

踩坑记录：第一版只引用 prefix/suffix 两个小常量，`-s -w` 下链接器把没被真正引用的 `yySealRecord` 整段删了，
自检永远报 `not_found`；现在用 `var yySealRecordData = []byte(yySealRecord)` 保活，注释写明原因。

**（b）TracerPid 调试器检测**（`:176`）。读 `/proc/self/status` 的 `TracerPid`，非 0 判被 ptrace。
**只写日志告警，不退出、不自杀**——这套东西跑在用户的 systemd 里，一次误报就是整台机子的工具箱挂掉，
而 systemd/部分监控/备份代理确实会短暂 ptrace。宁可漏报，不能自伤。

**（c）构建指纹 + 输出**。`YY_SELFTEST=1` 打印完整报告后 `os.Exit(0)`，不启动服务，供人工/CI 验证；
否则把报告追加到 `<dataDir>/security.log`（0600）后正常启动。

**（d）接线三查**：① 定义 `protect_selfcheck.go:291 yySelfCheckStartup()`；
② 调用 `main.go:4945`，在 `StartServer()` 内、`hub = NewSSEHub()` 之前——这个点是刻意的，
Linux/Windows 原生启动与 Android JNI 启动（`Java_..._AccountProcessService_startCore`）都经过 `StartServer`，一处接线覆盖三端；
③ 验证 `YY_SELFTEST=1` 有输出且 exit 0（第六节）+ 单测 `TestSelfCheckStartupWritesLog` 确认真的写了 `security.log`。

### 2.3 敏感常量收敛（新增 `upstream/protect_secrets.go`，154 行）

`strings youyuan | grep netease` 就能把通信面全捞出来，这是「拿到二进制就等于拿到配置」的直接原因。
10 段明文改成 XOR+hex 存储、运行时还原（`yySecDecode`，`:37`），**对外标识符与行为一律不变**，
调用点只换取值方式。还原结果落 `sync.Once` 缓存（`yySecLoad`，`:80`），热路径不重复解码；
编码损坏返回空串而非 panic——白名单拿到空串＝全部拒绝，是安全侧失败。生成器 `maintenance/gen_protect_secrets.py`（幂等）。

### 2.4 Android R8 + 资源压缩

新增 `android/app/proguard-rules.pro`（约 80 行，逐条写「为什么必须保」）；`app/build.gradle` release 段改为：

```gradle
minifyEnabled true
shrinkResources true
proguardFiles getDefaultProguardFile('proguard-android.txt'), 'proguard-rules.pro'
```

用 `proguard-android.txt` 而非 `-optimize` 版本：本工程有 JNI/JS 桥按名字调用的硬约束，激进优化收益小、误伤面大。

**关键取舍**：`-keepnames class org.youyuan.toolbox.**` 只保**类名**，允许成员改名与裁剪。三处名字硬约束：
① Go 用 `FindClass("org/youyuan/toolbox/FloatingBridge")` 按字符串找类（`libmain.go:31`）；
② JNI 导出符号 `Java_org_youyuan_toolbox_MainActivity_setDataDir` 由「Java 侧声明的方法名」拼出，改名即断链；
③ WebView `addJavascriptInterface` 暴露的对象由 JS 按方法名调用（`MainActivity.java:122/271…`）。
所以「App 自己的类名混淆」本次**刻意没做**：要做必须先有真机逐项冒烟，否则就是「混淆成功、功能全挂」。
本次拿到的是：未引用代码裁剪 + 资源压缩 + **第三方库（okhttp/okio/androidx/shizuku）整体改名**。

### 2.5 效果实测

release APK 83,860,135 B → 82,761,567 B（−1.05 MB，−1.3%）；`org.youyuan.toolbox` 真实类被改名 **0** 个
（仅合成类 `$$…`/`-IA`）；JNI 关键类与 `emit` 在 dex 中全部存在。降幅小是正常的——APK 95% 是 native 库，R8 管不到 `.so`。

## 五、风险与副作用

| 项 | 风险 | 现状 |
|---|---|---|
| TracerPid | systemd 不 ptrace 子进程；`gdb`/`strace` 运维时会命中（期望行为） | 只告警不退出，**不会**造成重启循环 |
| 封印自校验 | 后续 `strip`/`upx`/重签/手工替换都会让封签失效 | 只告警 + 写 `security.log`，**不阻断启动** |
| 封印与自动更新 | 若将来「篡改即拒服务」，必须先让更新流程也走封印，否则自更新一次就自锁 | 注释已写明，本次不启用阻断 |
| 启动开销 | 每次启动读整个二进制算 sha256 | 实测自检总耗时 **0.278 s**（含进程启动），Linux 约 +150–250 ms |
| `YY_SELFTEST=1` | 会让进程 `os.Exit(0)` | 仅供人工/CI；**生产 systemd 单元里绝不能设** |
| R8 | 类名已核对保名，但**未做真机安装冒烟** | 上线前必须真机跑主流程：启动、悬浮窗、JS 桥、Python 插件、更新 |
| `shrinkResources` / 封印步骤 | 前者误删动态查询资源；后者 Python 缺失会中断构建 | 已核查全工程仅 2 处 `getIdentifier`（均查 `"android"`）；封印失败即中断是**故意的 fail-fast** |
| 共享工作树 | 期间 `upstream/` 被同组并发修改，中途 `go build` 因 `yyQQAIModeAuto` 重复声明失败过一次 | 已沟通；最终验证跑在收敛后的代码上（第六节） |

**附：本轮顺带核实的两条问题（未改代码，供决策）**
- `/api/youyuan/identity` 的 GET 没有任何 actor 校验，直接把 owner 的 `control_token` 写进响应（`youyuan_identity.go:127`）；
  服务只监听 `127.0.0.1`（`main.go:5243`），所以是**本机任意进程可读**，不是公网暴露。建议收成「仅回环 + Admin」。
- `yyQQPrivateKey` 用「secret 循环填充到 32 字节」当 Ed25519 seed（`youyuan_qq.go:865`）。这正是 QQ 官方机器人规范
  要求的推导方式，**换成 sha256 派生会让平台侧验签全部失败**，不能动；正解是校验时拒绝短于 32 字节的 secret。
- 红队同期有一份只读审计 `outputs/sec-vuln-hunt/报告.md`（H-1/H-2/H-3、M-4、M-7），与本报告的 P0 议题互补，建议一起看。
- 顺带修掉一处会误导安全评估的过期注释：`main.go:5241` 原写「绑定 0.0.0.0，允许局域网访问」，与实际 `net.Listen("tcp","127.0.0.1:…")` 矛盾，已按代码改正（纯注释，`go build` 仍 EXIT=0）。

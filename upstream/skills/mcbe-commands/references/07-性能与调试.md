# 七、性能与调试

基岩版指令系统最容易在规模上来后**卡顿/崩溃**，因为大量逻辑都跑在每刻循环里。

## 1. 每刻预算是硬约束

- 挂在 `tick.json` 的函数**每 tick 执行一次**（20 次/秒）。
- 每个 `execute ... as @e[...]` 都会对所有匹配实体执行一次；**分叉是指数级的**。
- 经验：单个 tick 函数里避免无 `c=` / `type=` 限制的 `@e`。

## 2. 分叉爆炸

```mcfunction
# 危险：实体多时瞬间几万次执行
execute as @e as @e as @e run say hi
```

**规则**：嵌套 `as`/`at` 前，必须确知每层的匹配数量，或加 `c=N` 限流。子弹/射线类逻辑用 `c=1`。

## 3. 实体堆积清理（扫地机）

```mcfunction
# 超过阈值就清理（用假玩家当计数器）
execute as @e[family=mob,family=!information,name=""] run scoreboard players add Entity Menu 1
execute if score Entity Menu matches 193.. run kill @e[family=mob,family=!information,name=""]

# 清理掉落物，但先做"贴地"处理避免误删
execute as @e[type=item,tag=!连锁] at @e unless block ~ ~0.2 ~ air run tag @s add 可疑
execute as @e[type=item,tag=可疑] at @e unless block ~ ~0.2 ~ air run fill ~ ~ ~ ~ ~ ~ air
tag @e[tag=可疑,type=item] add 连锁
```

要点：
- 清理前**倒计时提示**（`titleraw` + `playsound`），避免玩家物品突然消失。
- 白名单用一串 `type=!...`/`family=!...` 排除（动物、NPC、展示框、矿车等）。
- 廉价清理用 `kill @e[type=item]`（只清掉落物）。

## 4. 减少每刻开销的手段

- **用计分板当缓存**：把"每刻都要算"的结果算一次存进分数，后续直接读。
- **分频执行**：慢逻辑用计时器每 N 刻跑一次（`scoreboard players add 计时 假玩家 1` + `matches N`）。
- **用 `tag` 短路**：给已处理的实体打 tag，条件里排除，避免重复处理。
- **`if` 前置**：把最可能为假的 `if` 放前面，短路后续。

## 5. 调试方法

| 手段 | 用法 |
|---|---|
| actionbar 打点 | `titleraw @s actionbar {"rawtext":[{"text":"debug: "},{"score":{"name":"@s","objective":"X"}}]}` |
| 假玩家看全局量 | 把全局计数写进假玩家分数，用命令方块/tellraw 读出来 |
| 缩小目标范围 | 先用 `@a[tag=测试]` 只对测试玩家跑，验证后再放开 |
| 分步注释 | 把 tick 函数拆成多个 `# 步骤` 注释块，逐段启用 |
| 命令方块链调试 | 网易里 PULSE/CYCLE/CHAIN 三种方块分别试，看哪一步断链 |

## 6. 高频"写了不生效"排查顺序

1. **函数挂上了吗**：`tick.json` 的 `values` 里有没有这个函数；行为包有没有重载（`/reload` 或重进世界）。
2. **目标为空吗**：选择器是不是筛掉了所有人/实体。
3. **分数没初始化吗**：`scoreboard objectives add` 有没有执行；默认值是不是 0 而不是你想要的值。
4. **状态没推进吗**：上一步的赋值有没有真的改变分数（用 actionbar 打点）。
5. **顺序问题吗**：同一 tick 内先读后写/先写后读，结果完全不同（见战斗篇"先发效果后扣分"）。
6. **版本语法吗**：旧语法 `execute @a ~~~` 和新语法 `execute as @a at @s run` 不能混在一个词根里。

## 7. 已知基岩版 bug（写的时候绕开）

- 同一个 `execute` 里 `anchored` 写第二次不生效。
- `anchored eyes` 会错误影响相对坐标。
- 深度优先分叉在嵌套 `as`/`at` 时行为与 Java 不同。

## 8. 参考体积

- 素材里一个完整雪球菜单函数约 240 行 / 30KB；
- 坐标系统约 104 行；
- 战斗系统（子弹+伤害+换弹）约 800 行。
- 结论：**单函数别太长**，按功能拆成多个 `.mcfunction`，`tick.json` 只挂"主循环"，子逻辑用 `function xxx:yyy` 调用。
